Builder Brief — 3D Fighters & Jam Fight

Everything another AI needs to rebuild our 3D fighter work with no other context. Every number, data row, and code block below is copied from the production sources (the gamepress rigkit, the Fight Engine library, and the live Jam Fight build), not paraphrased from memory. Where a value was measured by running the game, the measurement is stated next to the claim.

1. What this is

Jam Fight is a 1v1 streetball fighting game — NBA Jam × Street Fighter on a half court, portrait phone-first. Two action-figure fighters dribble, shoot, dunk, steal, and beat each other up under streetball possession rules (make-it-take-it, take-back) with a real fighting layer on top (one attack button driving an automatic 5-move combo chain, signature special moves, knockdowns, KOs). First to 21 or the highest score when the 3:00 clock dies. It was built by an AI (Gemini 4 Neon) in AI Studio runs, then audited, torn down, and generalised into the reusable kit this brief documents. The stack, bottom to top:

  • rigkit figures — characters are data rows fed to one parametric builder: ~60 rigid primitive meshes bolted onto named pivot groups. No skinning, no bones, no weights, anywhere. Animation is small mathematical pose programs eased through one exponential damper (§2).
  • toon look — stepped cel shading + inverted-hull ink outlines + a halftone dot screen that lives only in the shade. Three ingredients, exact recipe in §3.
  • frame-data combat — a deterministic 60 Hz, DOM-free simulation core where every move is a data row (startup / active / recovery / damage / hitstun / blockstun / pushback / hitstop / cancel window / type / height). Seeded RNG; same seed + same inputs = same match, hash-proven (§5).
  • the 3D court — a three.js scene: low close portrait camera, instanced crowd, comic SFX callouts, painted court with halftone shading. Framing law: fighters occupy 31–33% of frame height; the scene fills the frame; zero dead foreground (§6).
  • touch controls — the gptouch standard: floating joystick on the left half, round buttons bottom-right, merged with keyboard (§7).

Design stance that produced all of it: ask for tools and systems, not content (a parametric figure factory, a move-table engine), pin every choice you care about (an AI builder fills unspecified choices silently), and prove by running — tests, probes, and screenshots at phone size, never by reading your own summary (§8).

2. The figure system — characters are data rows

2.1 The model

A character is one CharacterParams row. One builder function (buildHumanoid(params)) turns any row into a rig: ~60 primitive meshes (57–65 per figure; a slider-creator variant measured 74–82) rigidly parented to a tree of THREE.Group pivots. Limbs are pivot-at-top tapered cylinders — geometry translated so it hangs from the joint origin, so rotating the group swings the limb from the joint. Joint spheres at deltoid, elbow, and knee plug the gaps so bends never show a crack. The torso is a lathe; chest art is a canvas texture wrapped on it. The hand is three boxes (palm, curled-finger block, thumb) — never posed, reads by silhouette. The sneaker is four parts (sole, upper, ankle collar, toe cap).

interface BodyParams {
  width: number;      // lateral bulk multiplier — drives EVERY radius (torso, deltoids, thighs, calves)
  height: number;     // overall height multiplier. Total height ≈ 2.12 × height world units
  headScale: number;  // ~1.3 gives the exaggerated arcade look
  handScale: number;  // ~1.3 for big arcade hands
}

interface Palette {           // hex colours, one per material zone
  skin: number;
  jersey: number;             // torso cloth (also the torso-texture base colour)
  shorts: number;
  trim: number;               // belt / trim
  hair: number;
  band: number;               // headband / wristband
  shoePrimary: number;
  shoeAccent: number;
  glove?: number;             // OPTIONAL 9th slot: glove leather for the hands.
                              // Undefined = bare skin hands. (Sprite-sampled Ryu needed it:
                              // his fists are dark red-brown leather 0x7a2d1c, not headband red.)
}

type HairStyle = 'mohawk' | 'dreads' | 'fade' | 'buzz' | 'none';   // kit enum
// The game extends the union per roster: 'spiky' | 'spiky_ryu' | 'flattop_guile' |
// 'cap' | 'quills_sonic' | 'link_cap' | 'kong_tuft'
// Outfits and footwear are likewise enum-gated branches + canvas textures, never new geometry pipelines:
//   outfitStyle: 'jersey' | 'karate_gi' | 'airman' | 'plumber' | 'hedgehog' | 'tunic' | 'kong'
//   footwear:    'sneakers' | 'barefoot' | 'combat_boots' | 'work_shoes' | 'speed_shoes' | 'hero_boots'

interface CharacterParams {
  body: BodyParams;
  palette: Palette;
  hairStyle: HairStyle;
  torsoTexture?: THREE.Texture | null;  // canvas art for the lathe torso (jersey number, gi, emblem)
  proportions?: Partial<Proportions>; // per-row segment overrides, §2.3
  limbs?: { armScale?: number; neckLift?: number; shoeScale?: number; headband?: boolean }; // kit v2, §2.4
  toon?: { outlineWidth?: number; outlineColor?: number; halftone?: number; halftoneScale?: number; steps?: 3 | 4 }; // §3
}

Likeness = silhouette + signature props. Spend the geometry budget on the outline and the two props everyone recognises (a long cap + a shield; a muzzle, a tuft, a tie, 1.6× hands). All roster likenesses read at phone size in real gameplay framing by this rule alone.

2.2 Creator sliders and the 39-point stat budget

The creator schema runs every slider past the built-in roster's extremes — that is the point of a creator. Both slider-corner fighters (all-max and all-min) are test-verified to spawn with both feet planted at y = 0 (|min.y| < 0.015) and to score in a real match. Extremes are a test case, not a hope.

Stats: five stats — SPD (speed), SHT (shot), DNK (dunk), PWR (power), DEF (the health value, displayed as DEF) — on a 39-point total budget, the roster's best total. Four presets (THE GIANT, THE TANK, THE SPEEDSTER, THE ALL-ROUNDER) sit exactly at the cap; a seeded RANDOMISE builds to 33–39 and passes through the same enforcement.

Budget semantics — clamp, never reject. The cap is enforced by trimming: an imported 50-point fighter comes back 7/8/8/8/8 = 39. Out-of-range body values are clamped the same way (height 99 → 1.55). Malformed data (garbage text, missing keys, unknown enum values) IS rejected with a visible error — but an over-budget or out-of-range value never produces an error, and an over-budget fighter can never exist in-game. If your design needs rejection instead, that is a different contract — say so explicitly.

Each stat is an integer 1–10 (the roster's observed range is 4–10). The budget constrains the sum, not any single stat.

2.3 Proportions — the skeleton, and the feet-planted invariant

Every segment length is a fraction of body.height. These are the shipped defaults, verbatim:

export const PROPORTIONS = {
  hipHeight: 0.94,   // hip pivot height
  hipDrop: 0.05,     // hip pivot → leg pivot
  thigh: 0.42,
  calf: 0.39,
  ankleToSole: 0.08,
  torsoRise: 0.10,   // hip pivot → torso pivot
  shoulderY: 0.54,   // torso pivot → shoulder pivot (height)
  shoulderX: 0.31,   // torso pivot → shoulder pivot (lateral, × width)
  upperArm: 0.31,
  forearm: 0.29,
  headY: 0.72,       // torso pivot → head pivot
  hipX: 0.135,       // hip pivot → leg pivot (lateral, × width)
} as const;
The invariant: hipDrop + thigh + calf + ankleToSole must equal hipHeight (defaults: 0.05 + 0.42 + 0.39 + 0.08 = 0.94), so straight legs plant the sole exactly on y = 0. Ground contact is arithmetic, not IK — no raycasts. A gait-phase body bounce, a minimum shin bend of 0.08, and a painted contact shadow mask the rest. If you change one term of the sum, rebalance another — and grep every term of the sum for the scale factor: kit v1 shipped a bug where ankleToSole went unscaled, so at height ≠ 1 the feet floated by ankleToSole·(height−1) (0.032 units at height 1.4). Per-row proportions overrides merge over these defaults at build time, and per-frame code must read the rig's own stored proportions — never the global const (see the hipHeight bug, §4).

Head size is a parameter, not a modelling choice: head = 24% of total height at headScale 1.0. Kit reach/height caps at ≈1.24 (shoulder height is a fixed fraction of height, shoulderY 0.54) — armScale alone cannot buy more reach without going simian.

2.5 The pivots — 17 at runtime, 16 in the interchange standard

The runtime rig tree (root → bodyPivot → hips → torso → head, with two arm chains and two leg chains):

root
└─ bodyPivot          (yaw / lean channel — runtime only, NOT part of the interchange set)
   └─ hips
      ├─ torso
      │  ├─ head
      │  ├─ armL → forearmL → handL      (each a THREE.Group pivot)
      │  └─ armR → forearmR → handR
      ├─ legL → shinL → footL            (foot pivot sits AT the ankle — added by the channel extension)
      └─ legR → shinR → footR

GLB interchange standard: so a fighter built anywhere can be posed anywhere, exports carry every body part as a separate, unmerged, descriptively named mesh parented under one of 16 named pivot groups — root, hips, chest, armL_upper → armL_forearm → armL_hand, armR_upper → armR_forearm → armR_hand, legL_thigh → legL_shin → legL_foot, legR_thigh → legR_shin → legR_foot, head (chest = the runtime torso). Accessories export too, parented to their pivot. A posed export bakes the pose into node transforms; the neutral export is the same file at the neutral pose. This standard was verified by hand-decoding a real export: valid glTF 2.0, 61 distinct meshes, 78 nodes, 20 materials, all 16 pivots present in the correct hierarchy. The text-share format (Fighter Code JSON) is an 8-key schema that round-trips byte-identical; a share code is the fighter's data row.

Canvas-UV gotcha (bitten twice): where the lathe torso's front falls in u is NOT consistent across builds — the kit lathe's front is u = 0.25; the Figure Factory page's lathe (rotY = π/2) puts the front at u = 0.75. Do not trust any doc, including this one: run a debug-quadrant texture pass in your harness and draw chest art where your build actually puts the front.

2.6 Pose — 51 channels, one damper

A pose is a flat record of 51 channels. All angles are radians. Every channel defaults to the neutral value below and is eased by the one damper; a program writes only the channels it cares about.

bodyY        bodyPitch    bodyRoll     spin (number | null — see below)
hipsPitch    hipsYaw      hipsRoll
torsoPitch   torsoYaw     torsoRoll
headPitch    headYaw      headRoll
armLX  armLY  armLZ      foreLX  foreLY  foreLZ
armRX  armRY  armRZ      foreRX  foreRY  foreRZ
handLX handLY handLZ     handRX  handRY  handRZ
legLX  legLY  legLZ      shinLX  shinLY  shinLZ
legRX  legRY  legRZ      shinRX  shinRY  shinRZ
footLX footLY footLZ     footRX  footRY  footRZ
mouth  brow

NEUTRAL_POSE (non-zero defaults; everything else 0):
  armLZ 0.15, armRZ -0.15        (arms hang slightly out)
  foreLX -0.35, foreRX -0.35     (elbows carry a slight bend)
  shinLX 0.08, shinRX 0.08       (minimum knee bend)
  mouth 1.0  (mouth scale.y; ~2.5 = shouting)
  brow 0.14  (positive = aggressive, negative = pained)

The one damper makes the feel: poses are never snapped to. Every channel eases toward its target with damp = 1 − exp(−16·dt) (rate 16/s, time constant ≈ 63 ms, frame-rate independent). Transitions, anticipation bleed, and follow-through lag are all emergent from that single constant — it is THE feel knob (lower = floatier, higher = snappier; 16 is proven for move durations of ~0.3–1.0 s). The one exception: spin — when a program sets it non-null, body yaw = facingYaw + spin is applied without damping, because spin moves must track exactly.

History worth knowing: the channel set started at 19 fields (only the axes one game's moves needed). A step-data authoring tool (full Euler targets per pivot) forced the extension to 51 — projecting onto 19 had silently dropped real acting: a −0.977 rad head yaw in a punch, a 90° hand roll, all foot motion. The extension is purely additive: every added channel defaults to 0, no pre-existing program writes them, and the default path is bit-identical (regression-proven: harness screenshots md5-identical, joint dumps equal to ≤1.1e-16).

2.7 Pose programs — moves are functions, not keyframe clips

A pose program is a function of normalised time t ∈ [0,1] that writes target channel values into an output pose. The engine owns time (durations, hit windows, damage live in the engine's move table — pose program and hit window are authored in the same row, which is why hits land when the fist arrives); the rig only turns a state sample into a pose. Continuous signals come in through a context object the engine maintains:

interface PoseContext {
  momentum: number;      // 0..1 built-up speed
  lean: number;          // damped lean (e.g. ease toward momentum × 0.36 at 10/s)
  runPhase: number;      // advance: += actualSpeed × dt × 2.6 while moving
  dribblePhase: number;  // advance: += dt × (7.5 + momentum × 4.5) with ball, 5.6 idle
  squash: number;        // set 0.7–1.0 on landing by the engine; decay ≈ 5/s
  airY: number;          // jump height (engine physics / scripted arc)
  vy: number;            // vertical velocity (secondary motion)
  hasBall: boolean;  guarding: boolean;  moving: boolean;
  spinDir: number;       // ±1, for directional spin moves
  time: number;          // elapsed seconds (idle breathing, flutter)
}
type PoseProgram = (t: number, ctx: PoseContext, out: Pose) => void;

Four idioms cover a game. Sign conventions: rotation.x negative swings a hanging limb FORWARD; shin positive bends the knee backward; torsoPitch positive leans forward; armL/legL are the near side in side view, armR/legR the far side.

// IDIOM 1 — snap envelope for strikes: peaks at t≈0.69, fully returns by t=1.
export const snapEnv = (u: number): number => Math.sin(Math.min(1, u * 1.45) * Math.PI);
export const jabProgram: PoseProgram = (_t, _ctx, out) => {
  const snap = snapEnv(_t);
  out.torsoYaw = 0.55 * snap;
  out.torsoPitch = 0.18 * snap;
  out.armLX = -1.65 * snap;      // punching arm extends
  out.foreLX = -0.1;
  out.armRX = -0.9;              // guard arm stays home
  out.foreRX = -1.4;
  out.legLX = -0.28 * snap;      // brace
  out.legRX = 0.28 * snap;
  out.brow = 0.36;
  out.mouth = 1.9;
};

// IDIOM 2 — linear sweep for spins: an angle that accumulates across the whole move.
//   windmill arm:  out.armRX = -Math.PI * 0.5 - t * Math.PI * 2.2;   // full revolution + a bit

// IDIOM 3 — phase split for two-beat moves (tomahawk: 65% wind-up, 35% slam):
//   const cock = t < 0.65 ? -3.15 * (t / 0.65) : -3.15 + ((t - 0.65) / 0.35) * 1.95;
//   out.armRX = cock;

// IDIOM 4 — held constants for stances, plus ctx.time for breathing (see Ryu idle, §2.8).

Base layers run under every program: a phase-driven gait (stride 0.55 + momentum × 0.55, bounce |cos(runPhase)| × (0.06 + momentum × 0.06), torso counter-yaw swing × 0.18), a dribble arm that leaves the gait and follows the dribble clock, idle breathing. Held props are NOT attached to hands — the ball sits at fixed offsets, synced to the dribble arm by one shared phase clock. Authoring a new move = a name, an engine-side duration, one program, one trigger.

// The keyframed() helper the hadouken above is built with (from the same source).
// It mixes the 18 classic fields; direct-function programs (§2.7) can write any of the 51.
const POSE_FIELDS: Array<keyof Pose> = [
  'bodyY', 'bodyPitch', 'bodyRoll', 'torsoPitch', 'torsoYaw', 'headPitch',
  'armLX', 'armLZ', 'foreLX', 'armRX', 'armRZ', 'foreRX',
  'legLX', 'shinLX', 'legRX', 'shinRX', 'mouth', 'brow',
];
type Key = [number, Partial<Pose>];
function keyframed(keys: Key[], spinFn?: (t: number) => number): PoseProgram {
  const sorted = [...keys].sort((a, b) => a[0] - b[0]);
  return (t, _ctx, out) => {
    let a = sorted[0]; let b = sorted[sorted.length - 1];
    if (t <= a[0]) { b = a; }
    else if (t >= b[0]) { a = b; }
    else { for (let i = 0; i < sorted.length - 1; i++) {
      if (t >= sorted[i][0] && t <= sorted[i + 1][0]) { a = sorted[i]; b = sorted[i + 1]; break; } } }
    const span = b[0] - a[0];
    const k = span > 0 ? (t - a[0]) / span : 0;
    const smooth = k * k * (3 - 2 * k);   // smoothstep between keys
    for (const f of POSE_FIELDS) {
      const av = a[1][f] ?? (NEUTRAL_POSE[f] as number);
      const bv = b[1][f] ?? (NEUTRAL_POSE[f] as number);
      (out[f] as number) = av + (bv - av) * smooth;
    }
    if (spinFn) out.spin = spinFn(t);   // spin is authored separately — it must track exactly
  };
}

3. The look — toon is three ingredients, not a vibe

The Jam Fight look is exactly three ingredients. Missing any one of them reads as a different, cheaper game.

3.1 Stepped cel shading

  • MeshToonMaterial with a cached gradient-map ramp: 4 steps [105, 160, 212, 255] or 3 steps [120, 190, 255], NearestFilter — hard shadow terminator, no specular falloff.
  • Face features (eyes, pupils, brows, mouth) switch to flat MeshBasicMaterial: crisp ink shapes instead of lit blobs.
  • API: renderMode: 'toon' + params.toon (outlineWidth, outlineColor, halftone 0..1, halftoneScale, steps 3|4), overrides merged field-by-field. In the gamepress character builder the port is toon(color, { halftone, halftoneDensity = 30 }) and buildHumanoid({ outline, halftone }), defaults off.

3.2 Inverted-hull ink outlines — and the lesson that cost two attempts

  • One BackSide dark shell child per mesh, displaced in the vertex shader along the vertex normal by a world-space width (default 0.026 in the kit; the gamepress port's addOutlines(root, width = 0.018, color = 0x17120d, minRadius = 0.05)), so thickness is uniform at any figure scale.
  • Skip small parts: any part whose bounding sphere × world scale < 0.06 m gets no hull — eyes, pupils, brows, mouth and toes measure below the threshold, so they are never swallowed. Hulls cast/receive no shadow and ignore raycasts.
The raw-normal rule. The first outline implementation displaced along objectNormal — which MeshBasicMaterial's shader program never declares (it skips the normal chunks). The outline program failed to compile ('objectNormal': undeclared identifier) and the hulls silently never rendered. What looked like "thin outlines" for two attempts was the cel terminator plus dark geometry. Two rules: (1) displace along the raw normal attribute, never objectNormal, in a MeshBasicMaterial hull; (2) prove outlines by pixel probe, not by eye — the fix was verified by an outline on/off pixel diff (6,238 pixels differ at width 0.026, 0 shader errors). A silent shader compile failure looks exactly like a subtle effect.

3.3 Halftone — dots that live only in the shade

  • A fragment-shader injection recomputes the first directional light's cel gradient per pixel and grows dots as the gradient darkens: no dots in the light, fat dots in the shadow step. Object-space via each part's own UVs (attach a plain white map to map-less parts so UVs exist).
  • Do NOT bake halftone into canvas textures: baked dots print everywhere — lit skin, white cloth — and read as leopard print / measles. Baked is kept only for unlit/sprite contexts, and is the only halftone form that survives GLB export, at that cost.
  • At scene level the same print language extends past the fighters: halftone dots baked into the court texture, a halftone-band sunset shader in the sky, and comic SFX starburst callouts (WHAM! / SWISH! / BAM! / SHORYUKEN! / HADOUKEN!) rendered as SVG bursts over the HUD.

Two more field lessons from the same pass. Option-bag merges eat defaults: an explicit undefined from a caller's options silently wiped the halftone default for a whole attempt — merge field-by-field and treat undefined as "not passed". And toon is a renderer-side mode: GLB export carries geometry, pivot hierarchy, part colours and canvas maps, but NOT the cel stepping (glTF has no toon ramp), NOT the shader halftone, and NOT the outlines (hulls export as undisplaced duplicate geometry that z-fights). An exported GLB is a smooth-shaded figure; the look appears when a three.js scene renders it with this kit.

3.4 The owner's law — a style variant must change construction

Rule: a render mode that only changes the surface — shading model, texture treatment, palette, output resolution — on one identical construction reads as a recolor at phone size, whatever the pipeline does underneath. The figure's geometry, proportions and silhouette carry the look-and-feel; a mode that is supposed to change look-and-feel must change geometry and proportions too (a chibi proportion row for Anime, a chunkier low-poly rebuild for PS1, and so on). Surface treatments are finishes, not modes. The check is silhouette IoU against the base figure (§4): if the silhouette barely moved, the "mode" didn't.

Evidence: nine surface modes (Anime, 16-bit, 8-bit, Paint, Watercolour, Clay, PS1, Sticker, Real) were built with genuinely working mechanisms — 2-step cel ramps, Bayer-dithered 144×180 render targets snapped to a 52-colour NES palette, ~1,250 directional brush strokes per part, vertex snap to a 168×132 clip grid, fingerprint bump maps — and the builder graded all nine PASS at 420 px panels. The owner graded the sheet: "Not good. Nothing changed other than slight colors. Exact same look and feel of the 3D character." The owner's verdict supersedes the builder's grades. Grade style work against the owner's eye at phone size, not against a mechanism checklist.

4. Matching a reference — the sprite-goal method

When a character has a ground-truth reference (a sprite, a render, a photo), the reference IS the target — set the goal as the reference image and measure against its pixels. Two numbers, both computed against the real reference:

  • Silhouette IoU — render alpha vs reference alpha, height-normalised, alignment searched. This is also the construction check for style variants (§3.4).
  • Palette ΔE — CIE Lab distance over reference-defined colour regions. The palette itself is sampled from the reference's pixels, never eyeballed.

The 3-attempt rule: push up to THREE attempts per item — each photographed at the same framing and judged against the original — pushing further each time (not colour only: density, dressing, models). A stop after attempt 2 needs a written, evidence-cited reason.

The bug this method caught (fix is in the kit): per-frame code reasserted hip height every frame from the global PROPORTIONS const, silently stomping any per-row hipHeight — attempts were scored with the pelvis stuck at default height, feet sunk ~0.11, invisible under bbox normalisation. The standard joint dump exposed it: pelvis byte-identical while knees/ankles moved. Rules that generalise: per-frame code must read the rig's own build parameters, never a global const the builder also read; and a joint dump is a better lie detector than a screenshot. Harness pattern: match mode is opt-in URL params — orthographic side camera at fixed figure height, chroma backdrop, flat ~1.0 irradiance light rig (so rendered colours are the authored palette, not the stage's tone mapping), per-attempt row overrides so attempts need no code edits. When tone mapping is off, rebalance flat-light intensities to ~1.0 total, or exposure error will masquerade as a palette regression.

5. The combat core — Fight Engine contract

A deterministic 60 Hz 2D fighting-game core as a DOM-free TypeScript library, plus a training-mode app on top. Verified by grep and by audit: no document, window, Math.random or Date.now anywhere in the engine source — its only randomness is a seeded PRNG (Mulberry32) whose state lives inside the engine state. Fighters are added with registerFighter() as pure data; there is zero fighter-specific logic in the engine.

5.1 Moves are data rows, full stop

Every move carries all of these fields (frame counts are in 60 Hz frames):

5.2 The rules that make it a fighting game

  • Hitstop: light 6f / medium 8f / heavy 11f, counter-hit +3f (a counter-heavy measured exactly 14f, frozen frames counted by an independent script). Data rows and sim agree.
  • Input buffer: 6 frames, and its TTL ticks only on non-hitstop frames — a heavy pressed during a jab's recovery, outside the cancel window, with no further input, fires the frame the jab ends. A dropped-input engine cannot do that; this is the test that separates a real buffer from a comment claiming one.
  • Motion recognition with a mandatory diagonal: quarter-circle-forward requires the chronological 2→3→6 inside a 14f window; the near-miss 2→5→6 does NOT fire. Near-miss rejection is half the feature.
  • Blocking matrix: low is blocked by crouch-back only; mid by stand-back or crouch-back; high (overhead) by stand-back only; throws are unblockable.
  • Throw tech window: 7 frames. Tech at +7f succeeds (0 damage); at +8f the throw completes for full damage (120). Tested at the boundary, not near it.
  • Juggle scaling: damage scales 100 / 90 / 80 / 70 / 60…%, floor 10% per successive juggle hit. An independent corner juggle (different seed and positions from the engine's own test) reproduced the exact scaled sequence [90+36+32+28+24] = 210.
  • Chip damage: 10%, specials only. A blocked normal costs 0 HP; a blocked 100-damage special costs exactly 10.
  • Rounds: 60-second rounds (3,600 frames), best-of-3 (first to 2 rounds).
  • Determinism, proven not asserted: a 600-frame scripted match (independent input stream, both fighters, full-state SHA-256 every 60 frames) produced identical hashes at every checkpoint under seed 42, and diverged under seed 43. When a prompt asks for determinism, name the hash test in the prompt.
  • An honest CPU: the lab opponent is restricted to delayed, screen-visible perceptual observations (14-frame delay) — it plays fair by construction instead of reading inputs.

6. Jam Fight — the game

6.1 Match rules

  • 1v1, half court, first to 21 or highest score at the 3:00 clock. Tied at 0:00 → overtime, sudden death, next basket wins. Baskets: +2 inside the arc, +3 beyond it, dunks +2.
  • Make-it-take-it: the scorer keeps possession; play resets at the top of the arc.
  • TAKE-BACK rule: after a change of possession (defensive rebound or a steal that crosses half-court possession), the new offence must dribble the ball back beyond the 3-point arc before a score counts. Scoring without clearing: the basket is void and possession flips to the opponent ("NO TAKE-BACK!"). A steal already beyond the arc needs no take-back. This rule is load-bearing — it is what makes the half court play like a full game.
  • Momentum movement: speed builds smoothly over ~2 s of moving in one direction and bleeds on a sharp turn or stop; the rig's lean, stride and dribble all read off the same momentum value (§2.7 context).
  • ON FIRE: 3 consecutive makes puts a fighter on fire until the streak breaks: sprint ×1.18, shot effective distance −2.4 (shots play as if closer), +0.14 shot bonus, a jagged flame crown at the feet and a flame shell on the ball.
  • Tricks: one trick move per fighter on a 2.0 s cooldown, with a dodge window that makes melee hits whiff.
  • Knockdowns and KOs: knockdown time 2.5 s; a full KO (health emptied by the fighting layer) takes 5.0 s and awards the opponent a free shot.

6.5 Current shipping rules (November 19, 2026 — the brief describes the game as it ships today)

No difficulty choice. The ROOKIE/PRO/ALL-STAR selector is deleted from the UI; a module constant GAME_DIFFICULTY = 'ROOKIE' feeds every match creation (initial load, match start, back-to-title), so the CPU always runs the ROOKIE profile. Jump shots rim out 25% at random. In startJumpShot — the single shot-outcome path both players resolve through — after the normal make roll: if (willMake && nextRand(state) < JUMP_SHOT_RIM_OUT_CHANCE) willMake = false; with JUMP_SHOT_RIM_OUT_CHANCE = 0.25. Net effect: even a perfect shooter makes at most ~3 of 4; shots stay easy, never automatic. It uses the game's own seeded RNG, so replays stay deterministic. Dunks and layups are exempt (they resolve through a different path and were not touched). Verified by sampling the real sim: 800 jump shots → 462 made = 57.75% realised vs 58.61% predicted (0.7814 × 0.75); dunks 40/40 scored, exactly as before.

6.7 Framing law and presentation

}
  • z-index: the touch overlay sits at z-index 1000 and covers the whole screen on touch devices — any in-game HTML button below 1000 is unreachable on phones while working fine in desktop tests. In-game HTML UI gets z-index ≥ 1100, and button verification must run in a touch-enabled context (touch tap + elementFromPoint check), never mouse clicks alone.
  • Use the standard for: platformers, brawlers, duel/fighting, run-and-gun, kart, shmup — anything with movement + 1–3 actions. Don't for tap-anywhere or drag-only games; the overlay would swallow the taps those games need.
  • iOS audio unlock recipe: on audio init, if (navigator.audioSession) navigator.audioSession.type = 'playback' (iOS 17+; without it the silent switch mutes WebAudio); play a 1-sample silent buffer inside the first user gesture; resume the context on every pointerdown/touchend and on visibilitychange (a suspended or interrupted context both need it); expose the AudioContext state in a debug handle so headless probes can prove it reads 'running'. Real-device verification is still a human gate.

8. Prove it — the verification discipline

Nothing in this brief was accepted from a builder's summary. Every claim above was verified by running the thing, most of them twice (the builder's own suite plus an independent probe). Reproduce that discipline:

8.1 The named test suites

Jam Fight engine — 11 tests (all behavioural, driving the real stepMatch): (1) momentum builds smoothly over ~2 s and bleeds on sharp turn or stop; (2) take-back: defensive rebound requires clearing beyond the 3pt arc before a shot counts; (3) take-back clears once the player dribbles beyond the 3-point line; (4) make-it-take-it keeps possession at the top of the arc, and 3 consecutive makes triggers ON FIRE; (5) fighting: 5-step auto-combo chain, auto-guard damage cut, ball pop loose, full-KO free shot; (6) trick move has a 2 s cooldown and its dodge window causes melee hits to whiff; (7) automatic dunk selection covers layup, free-throw leap, poster dunk, and showstopper dunks; (8) shot evaluation distinguishes OPEN vs CONTESTED and the honest AI produces valid inputs; (9) Ryu signature moves: Tatsumaki trick, Shoryuken Dunk, Hadouken combo finisher knocking the ball loose; (10) Guile signature moves: Sonic Boom shoves the defender back, Flash Kick Dunk, Flash Kick high block; (11) AI has zero rubber-banding: decision cadence identical whether leading or trailing by 14.

Fight Engine — 7 tests (the 6 the spec named, plus one the builder added): (1) frame-exactness — a scripted jab with startup 5 connects on frame 6, never 5; (2) hitstop — measured freeze frames equal the table (6/8/11, counter +3); (3) juggle scaling — a scripted 5-hit juggle deals the exact scaled sum (100/90/80/70/60%) with the 10% floor; (4) motion input — a recorded quarter-circle stream triggers the special, the near-miss does not; (5) determinism — two runs of seed 42 + identical inputs produce identical outcome hashes; (6) throw tech — inside 7f succeeds, at 8f fails; (7) combat invariants — high/low blocking matrix, 10% special-only chip, cancel-window edges (cancel at moveFrame 9 succeeds, at 12 fails).

8.2 The methods

  • Independent probe, not the builder's tests alone: write your own driver that feeds scripted inputs through the real sim and observes events, HP, positions, and freeze frames. The audits' probes re-derived headline numbers the builder never reported (AI cadence 112 vs 112; the juggle sum; throw tech at the exact boundary).
  • Determinism hash: scripted match, hash the full state at fixed intervals (SHA-256 every 60 frames over 600), same seed twice → identical at every checkpoint; a neighbouring seed must diverge. Jam Fight's RNG is a seeded integer hash in the match state (nextRand: t = state.rngState += 0x6D2B79F5, then imul/xorshift mixing) — replays stay deterministic because every random call, including the rim-out roll, draws from it.
  • Probability claims get sampled, not argued: any "X% chance" mechanic is verified by driving the real resolution path hundreds of times and comparing realised vs predicted within binomial noise (the rim-out: 800 shots, 57.75% realised vs 58.61% predicted; dunks 40/40 as the untouched control).
  • Art is accepted only as a full-size side-by-side against an independent ground truth (the original presenting the same coordinates, or real reference captures), comparing presentation, not just data — plus the measured checks: silhouette IoU / palette ΔE (§4), fighter height % and dead rows (§6.7), outline pixel-probes (§3.2), joint dumps over screenshots (§4). A visible anomaly is a stop-and-check, never a footnote.
  • Phone-size play check: serve the production build at production path depth (a build that passes at the wrong depth can still 404 its assets live), play it headless at 420×860 across real sessions — title → select → match → pause — with 0 page errors, in a touch-enabled context for buttons. Verify the served bytes after publishing, not the staged ones: read back byte size + a changed marker string after every push (a push reporting success has shipped stale bytes before), and poll the live URL until served bytes match — Pages lags minutes.
  • Performance honesty: a headless software-GL rate (this VM renders at ~3 FPS under SwiftShader) is not a phone measurement, in either direction. Ship the FPS readout and verify on hardware.
  • Inventory every AI-Studio export ZIP by file size before trusting it: one export arrived with six zero-byte scaffolding files (package.json, index.html, src/main.tsx, vite.config.ts, tsconfig.json, bun.lock) — sources intact, app unbuildable as delivered. A sibling export the same day was complete (37 files, zero zero-byte). It varies by run; check every time.

9. What to steal first — cold-start order

  1. The kit: one parametric builder, pivot-at-top primitives, joint spheres, the PROPORTIONS table with its leg-sum invariant. Build one figure and plant its feet at y = 0 at both slider corners.
  2. One fighter row: copy §2.8's shape — body, sampled palette, hair enum, a canvas torso texture (after a quadrant test for your build's front u). Then a second row that is only different data.
  3. The damper + pose programs: 1 − exp(−16·dt) on all 51 channels, the four idioms, base gait/dribble layers. Author idle + one strike; feel is done when the strike's fist and the engine's hit window agree.
  4. The toon pass: cel ramp, hulls displaced along the raw normal (pixel-probe them), shade-gated halftone. This is the look; everything else is a game wearing it.
  5. One move table: the §5 contract — 8 rows, all fields, hitstop by weight, a 6f buffer that survives hitstop, one motion input with near-miss rejection. Write the determinism hash test before you tune anything.
  6. The court and the rules: half court, WIN_SCORE 21, MATCH_SECONDS 180, make-it-take-it, take-back, momentum, ON FIRE at 3. The possession rules are the game; the fighting layer is the spice.
  7. The honest AI: profile-driven inputs, no score term anywhere, cadence measured ahead and behind. If you can't prove it's not cheating, players will assume it is.
  8. Controls last, to the standard: gptouch floating stick + round buttons, z-index ≥ 1100, iOS audio unlock — verified with touch taps, not mouse clicks.
