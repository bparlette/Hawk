The two-part model

Every port splits into two parts with different automation profiles — don't conflate them.

Part A — automated asset extraction (mechanical, generalizable). Scripts read your ROM and produce target-format assets: tiles, maps, sprite frames, collision grids, enemy tables, palettes. Tool it once per source platform.

Part B — manual logic reimplementation (game-specific, not mechanical). All gameplay — physics, enemy state machines, weapons, bosses — rewritten in the target's language from the annotated disassembly. This is the bulk of the work. Budget for it honestly.

Sound exception: write a minimal CPU interpreter for the source platform, run the game's own sound driver offline at build time, record audio-register writes per frame, convert to the target's format.

Workflow

1. Obtain and assert. Checksum (MD5) the ROM before any tool touches it. Record the disassembly commit used as reference.
2. Extract (Part A). Graphics decoder, sprite tables → atlases, collision grids, enemy placement. Check preview images by eye.
3. Reimplement (Part B). Routine by routine from the disassembly. Prototype feel on web first if useful, then commit to the target's integer math.
4. Convert sound. Interpreter + offline capture + register log → target format.
5. Adapt the screen. Retune spawns and view windows for the target's resolution.
6. Budget memory. Count worst-case resident tiles/sprites before adding actors.
7. Climb the verification ladder (below).

Verification ladder — a port is done when it passes all four, in order

1. Data assertions (automated). Checksum assert, tables asserted against disassembly, round-trip checks.
2. Visual comparison (manual). Rendered levels and collision overlays checked against the source.
3. Emulator bots (automated). Scripted playthroughs reaching every level/room/boss.
4. Hardware playthrough (manual). Flash cart, real console, played by a human. Emulators are not trusted alone.

Frame-rate conversion

Source and target rarely share a refresh rate (e.g. NES 60.1 Hz vs Virtual Boy ~50 Hz). Velocities × K, accelerations × K², where K = source_hz / target_hz. Convert durations proportionally. Don't model lag frames or sprite flicker.

What gamepress provides for ROM work

nesextract (lib/nesextract.mjs) — generic NES ROM asset extraction: iNES header parse, MD5 assert, CHR tile decode, OAM sprite parse, palette handling, tile-sheet PNG previews.
gbfixed.js (kit/gbfixed.js) — 8.8 fixed-point math for ROM targets, plus frame-rate conversion helpers.
Decomp mechanics (docs/DECOMP-REFERENCE.md) — extracted gameplay numbers/formulas from SM64DS, Melee, Galaxy, Pikmin 2 decomps.
